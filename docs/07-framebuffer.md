# 07. Framebufferとピクセル描画

## 1. Framebufferとは

Framebuffer（フレームバッファ）とは、画面に表示するピクセルの色情報を保持するメモリ領域である。

一般的なRGB形式のFramebufferでは、各ピクセルに対応するメモリへ色を書き込むことで、画面に画像や文字を表示できる。

例えば、画面解像度が1280×800で、1ピクセルが32bitの場合、ピクセルデータに必要なメモリは次のようになる。

\[
1280 \times 800 \times 4 = 4,096,000\ \text{bytes}
\]

約3.91MiBである。

Framebufferを利用すると、OSは高水準の描画ライブラリを使用せず、ピクセル単位で画面を制御できる。

ただし、Framebufferそのものは文字や図形を理解しない。文字、線、矩形などは、OS側がピクセルの集合として描画する必要がある。

## 2. Framebufferとディスプレイの関係

画面表示は、概念的に次のような構造になっている。

```text
OS
 └── 描画処理
      └── Framebufferメモリ
           └── ディスプレイコントローラ
                └── ディスプレイ
```

OSはFramebufferにピクセルデータを書き込み、ディスプレイコントローラがそのデータを読み取って表示する。

Framebufferへの書き込みは、通常のRAMへの書き込みと似ているが、デバイスやメモリマッピングの特性を考慮する必要がある。

また、Framebufferに書き込んだ内容が画面へ反映されるタイミングは、ディスプレイの更新方式などに依存する。

## 3. LimineからFramebufferを取得する

kanameOSでは、ブートローダとしてLimineを使用している。

LimineのFramebuffer Requestを利用することで、OS自身がGPUの初期化処理を実装する前から、利用可能なFramebufferの情報を取得できる。

取得した情報には、以下のような項目が含まれる。

| 項目 | 説明 |
|---|---|
| `address` | Framebufferの先頭アドレス |
| `width` | 横方向のピクセル数 |
| `height` | 縦方向のピクセル数 |
| `pitch` | 1行あたりのバイト数 |
| `bpp` | 1ピクセルあたりのビット数 |
| `memory_model` | ピクセルの表現形式 |
| `red_mask_size` | 赤成分のビット数 |
| `red_mask_shift` | 赤成分のビット位置 |
| `green_mask_size` | 緑成分のビット数 |
| `green_mask_shift` | 緑成分のビット位置 |
| `blue_mask_size` | 青成分のビット数 |
| `blue_mask_shift` | 青成分のビット位置 |

### `#[repr(C)]` が必要な理由

Limineが提供するデータ構造は、定められたメモリレイアウトに従って配置される。

Rustの通常の構造体ではフィールドの配置順序が保証されないため、外部のABIと対応する構造体には `#[repr(C)]` を指定する。

```rust
#[repr(C)]
pub struct Framebuffer {
    pub address: *mut u8,
    pub width: u64,
    pub height: u64,
    pub pitch: u64,
    // 以下省略
}
```

フィールドの順序や型がABIと一致していなければ、メモリを読み取れても誤った値として解釈してしまう。

なお、LimineのABI用構造体と、kanameOS内部で使用する `FramebufferInfo` は別の役割を持つ。

内部構造体には、外部ABIとの互換性が必要ない限り `#[repr(C)]` は不要である。

## 4. ピクセルのメモリ配置

### 4.1 bppとは

`bpp` は *bits per pixel* の略で、1ピクセルを表現するためのビット数を意味する。

例えば、

- 8bpp：1ピクセルあたり1バイト
- 16bpp：1ピクセルあたり2バイト
- 24bpp：1ピクセルあたり3バイト
- 32bpp：1ピクセルあたり4バイト

となる。

ただし、bppだけでは色の表現形式は決まらない。RGB成分のビット位置なども確認する必要がある。

### 4.2 RGB888形式

kanameOSのQEMU環境では、以下の形式を使用している。

```text
31       24 23       16 15        8 7         0
+----------+-----------+-----------+-----------+
|  未使用  |    Red    |   Green   |   Blue    |
+----------+-----------+-----------+-----------+
```

各色成分は8bitで、0〜255の値を持つ。

32bit整数としてのピクセル値は、

```rust
let pixel = ((red as u32) << 16)
    | ((green as u32) << 8)
    | (blue as u32);
```

で構成できる。

例えば赤色は、

```text
Red   = 255
Green = 0
Blue  = 0

pixel = 0x00FF0000
```

となる。

### 4.3 エンディアン

x86_64はリトルエンディアンを使用する。

そのため、整数値 `0x00FF0000` を `u32` としてメモリに書き込むと、低アドレス側から次のように配置される。

```text
アドレス    値
+0          0x00  Blue
+1          0x00  Green
+2          0xFF  Red
+3          0x00  未使用
```

整数のビット配置とメモリ上のバイト配置は区別する必要がある。

## 5. pitchとピクセルアドレス

### 5.1 pitchとは

`pitch` はFramebufferの1行分のバイト数を表す。

単純な32bppのFramebufferでは、

\[
pitch = width \times 4
\]

となる。

ただし、実際のFramebufferでは、行のアラインメントやパディングにより、`pitch` が `width × bytes_per_pixel` より大きくなる場合がある。

したがって、次の行へ移動する際は `width × 4` ではなく、取得した `pitch` を使用する。

### 5.2 ピクセルのオフセット

座標 `(x, y)` のピクセルが存在するバイトオフセットは、

\[
offset(x,y)=y\times pitch+x\times bytes\_per\_pixel
\]

で求められる。

今回の32bpp形式では、

\[
offset(x,y)=y\times pitch+x\times4
\]

となる。

ピクセルのアドレスは、

\[
pixel\_address=framebuffer\_address+offset(x,y)
\]

である。

例えば、解像度1280×800、pitch=5120の環境で `(100, 100)` を描画する場合、

\[
offset=100\times5120+100\times4=512400
\]

となる。

### 5.3 境界とオーバーフローの検証

座標が画面内に存在するためには、

```text
0 <= x < width
0 <= y < height
```

を満たす必要がある。

Rustの `u64` は負の値を表現しないため、実装上は上限を確認すればよい。

また、アドレス計算には整数オーバーフローの危険があるため、`checked_mul()` や `checked_add()` を利用する。

```rust
let row_offset = y.checked_mul(self.info.pitch)?;
let column_offset = x.checked_mul(bytes_per_pixel)?;
let offset = row_offset.checked_add(column_offset)?;
```

これらのメソッドはオーバーフローした場合に `None` を返す。

さらに、ピクセルの書き込み範囲全体が有効なメモリ領域内に収まることを保証する必要がある。

## 6. アラインメント

アラインメントとは、ある型の値を配置する際に要求されるアドレスの境界条件である。

x86_64環境では、一般的に以下の条件となる。

| 型 | サイズ | アラインメント |
|---|---|---|
| `u8` | 1バイト | 1バイト |
| `u16` | 2バイト | 2バイト |
| `u32` | 4バイト | 4バイト |
| `u64` | 8バイト | 8バイト |

例えば、`u32` を書き込む場合、書き込み先のアドレスは4の倍数である必要がある。

kanameOSでは32bppのFramebufferを `u32` として扱うため、初期化時に以下を検証する。

```rust
(info.address as usize).is_multiple_of(4)
info.pitch.is_multiple_of(4)
```

これにより、各ピクセルの先頭アドレスが4バイト境界に揃う。

x86_64のCPUはアラインメントがずれたメモリアクセスを実行できる場合があるが、Rustの `write_volatile::<u32>()` が要求するアラインメントを無視してよいわけではない。

## 7. volatile書き込みとunsafe

### 7.1 `write_volatile()` とは

`core::ptr::write_volatile()` は、volatileなメモリ書き込みを実行する関数である。

```rust
unsafe {
    core::ptr::write_volatile(pixel_ptr, pixel);
}
```

通常のメモリアクセスでは、コンパイラが不要と判断した書き込みを最適化で省略する場合がある。

volatileアクセスは、コンパイラに対して、そのメモリアクセスを観測可能な操作として扱うよう要求する。

Framebufferのようなデバイスに関連するメモリ領域で利用される。

ただし、volatileは以下を保証しない。

- ポインタの有効性
- メモリへの書き込み権限
- 排他制御
- CPU間の同期
- ハードウェア側の表示更新完了

### 7.2 なぜunsafeが必要なのか

生ポインタへの書き込みは、Rustの借用チェッカーだけでは安全性を証明できない。

そのため、呼び出し側または実装側が以下の条件を保証する必要がある。

- 対象メモリが有効であること
- 書き込み可能な領域であること
- 必要なサイズとアラインメントを満たすこと
- 競合するアクセスが存在しないこと
- 対象メモリが必要な期間、有効であること

kanameOSでは `Framebuffer::new()` を `unsafe fn` とし、初期化時に呼び出し側がメモリの有効性などを保証する設計としている。

一方、`put_pixel()` は安全な公開メソッドとし、内部にunsafeな書き込み処理を閉じ込めている。

```text
Framebuffer::new()   unsafeな初期化契約
        |
        v
put_pixel()          安全な描画API
        |
        v
pixel_offset()       座標検証
        |
        v
write_volatile()     unsafeなメモリ書き込み
```

安全な公開APIを成立させるためには、初期化時の契約だけでなく、構造体の内部状態がその後も不変条件を満たすよう設計する必要がある。

## 8. 矩形描画

矩形の塗りつぶしは、`put_pixel()` を繰り返し呼び出すことで実装できる。

```rust
pub fn fill_rect(
    &mut self,
    x: u64,
    y: u64,
    width: u64,
    height: u64,
    red: u8,
    green: u8,
    blue: u8,
) {
    let end_x = x.saturating_add(width).min(self.info.width);
    let end_y = y.saturating_add(height).min(self.info.height);

    for py in y..end_y {
        for px in x..end_x {
            self.put_pixel(px, py, red, green, blue);
        }
    }
}
```

`fill_rect()` 自身は、生ポインタやメモリレイアウトを意識する必要がない。

これは、低レベルの描画処理を抽象化した利点である。

また、`&mut self` を使用することで、呼び出し中はFramebufferを可変借用する。

所有権は呼び出し元に残り、メソッドの終了後に再び描画できる。

## 9. ビットマップフォントと文字描画

Framebufferは文字の形を理解しないため、文字を表示するにはフォントデータが必要になる。

最も単純な方法の一つが、ビットマップフォントである。

8×8ピクセルの文字なら、各行を8bitで表現することで、1文字を8バイトで保持できる。

例えば、文字「A」は以下のように定義できる。

```rust
pub const FONT_A: [u8; 8] = [
    0b00011000,
    0b00100100,
    0b01000010,
    0b01111110,
    0b01000010,
    0b01000010,
    0b01000010,
    0b00000000,
];
```

文字の描画では、各行のビットを左から順に調べる。

```rust
let mask = 0x80u8 >> col;

if row_bits & mask != 0 {
    // 対応する位置にピクセルを描画する。
}
```

ビットが1の場合のみ `put_pixel()` を呼び出せば、文字の形を描画できる。

この方式では、フォントデータの保持と実際のピクセル描画を分離できる。

## 10. kanameOSの設計方針

Framebufferに関する処理は、次のように責務を分離する。

```text
boot/
 └── limine.rs
      └── ブートローダとのABI・情報取得

graphics/
 ├── framebuffer.rs
 │    ├── Framebufferの初期化
 │    ├── ピクセルアドレスの計算
 │    ├── put_pixel()
 │    ├── fill_rect()
 │    └── draw_char()  ※現時点の実装
 │
 └── font.rs
      └── ビットマップフォントデータ
```

今後は、文字描画を独立したモジュールへ移すことも検討する。

設計上、特に重視する原則は以下のとおりである。

1. **高凝集**：各モジュールが明確な責務を持つ。
2. **疎結合**：上位の描画処理がメモリ操作の詳細に依存しない。
3. **unsafeの局所化**：生ポインタ操作を限られた箇所に閉じ込める。
4. **不変条件の維持**：初期化時に検証した条件を描画中も保つ。
5. **可読性・保守性**：描画処理を小さな関数に分割する。

## 11. 現在の実装と今後の課題

現時点で、以下の機能を実装している。

- Framebuffer情報の取得
- Framebuffer形式・サイズの検証
- ピクセルアドレスの計算
- アラインメント検証
- RGBピクセルの描画
- 矩形の塗りつぶし
- 8×8ビットマップ文字「A」の描画

今後の課題：

- `draw_char()` の汎用化
- ASCII文字への対応
- `draw_text()` による文字列表示
- 描画モジュールの責務整理
- Framebufferメモリの所有権・有効期間の厳密化
- 画面クリア、改行、スクロールなどのコンソール機能
- 境界条件や不正なFramebuffer情報に対するテスト

特に、現在の `is_supported()` は数値上の整合性を確認するものであり、任意のポインタが実際に有効なメモリを指すことまでは証明できない。

安全な描画APIを維持するため、今後もunsafeの契約とFramebufferへのアクセス管理を明確にしていく。

---

## まとめ

Framebufferは、OSが画面表示を制御するための基本的な仕組みである。

その本質は、**二次元のピクセル座標をメモリアドレスへ変換し、対応する色情報を書き込むこと**にある。

kanameOSでは、この低レベルのメモリ操作を `put_pixel()` に集約し、その上に矩形描画や文字描画を構築している。

この構造は、今後のテキストコンソールやグラフィックス機能の基盤となる。
